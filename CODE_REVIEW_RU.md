## Критические проблемы (безопасность и логика)

1) Непоследовательные возвращаемые значения в Voucher::getStatus() — ломает логику проверки статуса
- Файл: app/Models/Voucher.php (метод getStatus)
- Проблема: в некоторых ветках метод возвращает строковые литералы на английском ('USES_LIMIT_REACHED'), а в других — обёрнутые в перевод __() значения (например, `return __('EXPIRED')`). В контроллерах и финальной логике код сравнивает результат с литералами вроде 'EXPIRED' или 'VALID'. Из-за перевода сравнение всегда провалится при локализации отличной от английского.
- Влияние: функционал выкупа ваучеров (redeem) и отображения статуса может работать некорректно — просроченные ваучеры могут не распознаваться, лимиты использований — не применяться.
- Рекомендация по исправлению:
  - Привести getStatus() к единому контракту: возвращать константы (строки) без применения __() — например 'VALID', 'EXPIRED', 'USES_LIMIT_REACHED'.
  - Перевод выполнять в месте отображения (во view или контроллере), например: `__($voucher->getStatus())` или через маппинг статусов в человекочитаемые строки.
  - Объявить const STATUS_VALID = 'VALID' и т.п. в модели для избежания опечаток.

2) Гонка (race condition) при выкупе ваучера (redeem)
- Файлы: app/Http/Controllers/Admin/VoucherController.php (redeem), app/Models/Voucher.php (redeem, getStatus)
- Проблема: логика проверяет статус ваучера через подсчёт использований ($this->users()->count() >= $this->uses) и затем выполняет attach/инкремент без транзакции или блокировки. При параллельных запросах это может привести к превышению лимита uses.
- Влияние: возможна выдача кредитов сверх лимита ваучера, двойные записи pivot-таблицы user_voucher, неконсистентные данные и финансовые потери.
- Рекомендация по исправлению:
  - Выполнять редим ваучера в транзакции DB::transaction. При необходимости использовать SELECT ... FOR UPDATE на строке ваучера либо блокировку по id, чтобы убедиться в консистентности: получить текущий count/uses и выполнить attach/инкремент атомарно.
  - В pivot-таблице `user_voucher` поставить составной уникальный индекс (voucher_id, user_id), чтобы prevent duplicate attaches; перед attach использовать attachWithoutDetaching / syncWithoutDetaching и проверку exists(), либо использовать try/catch на уникальный индекс.

3) XSS — вывод данных пользователей/ролей без экранирования в HTML, используемый в rawColumns
- Примеры:
  - app/Http/Controllers/Admin/VoucherController.php -> usersDataTable: возвращается '<a ...>'.$user->name.'</a>' без e() экранирования.
  - app/Http/Controllers/Admin/UserController.php -> editColumn('role'): формирует `<span style='background-color: $role->color' class='badge'>$role->name</span>` без экранирования name и color.
- Проблема: если name/role->name/role->color содержат пользовательский ввод (например, при создании роли через UI) — возможна XSS или CSS-инъекция.
- Влияние: удалённое выполнение скриптов у админов / утечка сессий.
- Рекомендация по исправлению:
  - Всегда экранировать пользовательские данные перед вставкой в HTML. Использовать e($user->name) или `htmlentities`.
  - Для цвета валидировать значение (например, regex `/^#[0-9A-Fa-f]{3,6}$/`) или использовать заранее определённый набор цветов.
  - По возможности избегать raw HTML в контроллерах — формировать безопасные данные и использовать blade-шаблоны с {!! !!} только для доверенного HTML.

4) Неправильные преобразования дат в CouponController
- Файл: app/Http/Controllers/Admin/CouponController.php
- Проблема: в editColumn('expires_at') и editColumn('created_at') используются Carbon::createFromTimestamp($coupon->expires_at) и Carbon::createFromTimeString($coupon->created_at). Если поле уже хранится как datetime/строка/Carbon, эти вызовы некорректны и могут бросать исключения.
- Влияние: ошибки при рендеринге datatables, зависания админ-панели.
- Рекомендация по исправлению:
  - Использовать `$coupon->expires_at` как Carbon-экземпляр (если поле cast-ится в модели) или `Carbon::parse($coupon->expires_at)` безопасно. Для created_at: `$coupon->created_at->toDateTimeString()`.
  - Привести в модель `protected $casts = ['expires_at' => 'datetime'];` если ещё не сделано (похоже уже есть для Voucher — проверить и для Coupon).

5) Валидатор логина (LoginController::username и login) — потенциальная логика поля
- Файл: app/Http/Controllers/Auth/LoginController.php
- Замечание: метод username() берёт `request()->input('email')` и решает, является ли ввод email'ом или именем; однако если форма отправляет поле 'login' или 'username', код не увидит его. Это допустимо, если форма использует поле email для обоих вариантов, но нужно документировать.
- Рекомендация: либо принимать общий параметр (например 'login'), либо в username() смотреть несколько параметров: email, username, login.

## Проблемы качества кода и устойчивости

6) SQL в datatables: selectRaw с двойными кавычками
- Файл: app/Http/Controllers/Admin/VoucherController.php -> dataTable (selectRaw SQL CASE .. THEN "EXPIRED" ...)
- Проблема: в selectRaw используются двойные кавычки для строковых литералов в SQL. В MySQL в зависимости от sql_mode (ANSI_QUOTES) двойные кавычки могут трактоваться как идентификатор. Это снижает портируемость и может сломаться на некоторых конфигурациях.
- Рекомендация: использовать одинарные кавычки в SQL: WHEN ... THEN 'EXPIRED' или построить CASE в PHP после получения данных.

7) Преобразование денежных значений и мутация credits
- Файлы: app/Models/Voucher.php (credits Attribute), app/Models/User.php (credits usage, increment)
- Проблема: в Voucher::redeem вызывается `$user->increment('credits', $this->credits);`. Поскольку в модели есть set-мутатор для credits, поведение $this->credits (возращаемое значение) и то, в каких единицах хранится значение (центов или единиц), может быть неоднозначно. increment напрямую обновляет колонку в БД, минуя мутацию set:. Если $this->credits хранится в центах, передавать нужно именно целое число; если в единицах — привести.
- Рекомендация: документировать единицы (cents vs units) и унифицировать: использовать явные методы например `getCreditAmountForDatabase()` и использовать DB::raw или `$user->increment('credits', $amountInDatabaseUnits)`.

8) Использование get()->isEmpty() вместо exists() для проверок наличия
- Пример: VoucherController::redeem проверяет `if (! $request->user()->vouchers()->where('id', '=', $voucher->id)->get()->isEmpty())` — это делает запрос и загружает коллекцию. Лучше использовать `exists()` для производительности.
- Рекомендация: заменить на `->where(...)->exists()`.

9) Возможные проблемы с массовым удалением в User::deleting
- Файл: app/Models/User.php (boot static::deleting handler)
- Проблема: при удалении пользователя выполняются удаления и detach'и без chunking и без транзакции. Для пользователей с большим количеством связанных записей это может привести к таймаутам и неконсистентным состояниям.
- Рекомендация: использовать DB::transaction, обрабатывать большие наборы через chunk() или cursor(), и при удалении серверов/платежей использовать фоновые задачи (jobs) при больших объёмах.

## Производительность

10) Дататейблы: N+1 и загрузка связей
- Файлы: контроллеры, возвращающие datatables (Users, Vouchers и т.д.)
- Проблема: при формировании datatable запросы могут приводить к N+1 при извлечении ролей, discordUser и т.п.
- Рекомендация: использовать `with()` нужные связи в базовом query для datatables и использовать `->select` с необходимыми полями.

## Малозначительные замечания / улучшения

13) LastSeen Middleware: условие `if (config('app.env', 'local') == 'local')` — лучше проверять `app()->environment('local')`.

14) Подключение PterodactylClient в User::__construct
- Файл: app/Models/User.php — в конструкторе модели создаётся клиент PterodactylClient. Это приводит к созданию зависимостей при загрузке модели (например при миграциях/фабриках), и усложняет тестирование.
- Рекомендация: использовать ленивую загрузку или DI через сервис/репозиторий, либо фабрику/сервис, а не напрямую в конструкторе модели.
